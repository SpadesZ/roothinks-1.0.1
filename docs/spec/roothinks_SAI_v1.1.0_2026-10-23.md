## 1. 本次更新與現況界線

v1.0.1 著重模組、技術與檔案流；v1.1.0 增加「研究者如何形成判斷、如何交給下一個模組、如何與教授完成修訂」的契約。

本版新增重點：

- 搜尋結果、上傳 PDF 與可引用文獻以同一份研究文獻清單操作。
- 人類選材、否決理由、假設、條件與章節取捨可被確認、傳遞、修訂與追溯。
- 研讀比較以研究問題和可比較條件為中心；不把字詞重疊、缺少資料或模型故障當成研究結論。
- 教授意見能回到學生工作區，連到相應版本與處理回覆。
- 寫作須保留作者的論證與限制，並揭露未確認的 AI 新增主張。
- 投稿先接通一條完整、可離線使用的 DOCX 輸出，再逐步擴充模板與其他格式。
- 對全站模型管理、共用筆記、長任務、保存結果與研究品質建立明確驗收。

## 2. 產品目標與使用者

Roothinks 的目標是協助研究者把「我為什麼研究這個問題」逐步轉成「有證據、有界線、由作者確認的研究稿件」。系統要減少資料搬運與重複說明，保留人的選擇與責任。

### 2.1 主要角色

| 角色 | 核心工作 | 首頁應先回答 |
|---|---|---|
| 研究員／研究生 | 找文獻、核對、比較、記錄推論、撰稿與回應審查 | 我上次做到哪裡、哪些內容沒存好、下一步需我判斷什麼 |
| PI／Co-PI | 確認研究問題、選材、主張界線及整體稿件 | 哪些決策待確認、研究證據與稿件是否一致 |
| 教授／審閱者 | 看改稿差異、核對主張、給意見與確認回覆 | 這次改了什麼、上次意見處理了沒有、證據在哪裡 |
| 限定共同作者 | 編輯被指派的章節、回覆相關意見 | 我能看／能改哪些內容、哪些工作分派給我 |
| 系統管理者 | 全站模型、費用上限、服務與資料恢復 | 哪個任務失敗、影響誰、如何恢復且避免重複計費 |

學術角色、專案操作權限、系統管理權限為三件不同的事。PI 或教授身分不自動等於全站系統管理者；作者欄位中的人名也不等於已授權帳號。

### 2.2 非本版目標

不以 AI 偵測器分數作為作者性或品質指標；不追求刻意加入錯字或偽裝人寫。不自動捏造實驗、數值、引用、作者貢獻或可用性聲明。不在沒有量測依據時直接更換資料庫、增加多代理或重寫 OCR 管線。不自動寄送或投稿。

## 4. 目標工作流程與資訊架構

使用者流程：**釐清問題 → 收集與篩選文獻 → 核對並形成判斷 → 寫作 → 審查修訂 → 輸出稿件**。

五大模組保留為領域邊界，但畫面依使用者工作命名：PAQ 為「研究定位」、Literature 為「文獻庫」、Study 為「閱讀與比較」、Manuscript 為「寫作」、Submit 為「輸出」。Mentor 為角色入口「審閱與回覆」；模型管理置於獲授權者的系統設定。

流程允許返回前一步、直接匯入既有手稿、先讀文獻再修訂問題；不強迫研究者依固定編號全部走完。返回修訂時，系統指出哪些下游主張／稿件／輸出需要重核，而不刪除既有成果。

### 4.1 核心使用情境

1. **PDF 起步**：研究者上傳一篇 PDF → 同一文獻項目出現 → 選擇需要的處理 → 核對原文 → 留下納入理由 → 筆記與段落使用同一來源。
2. **問題起步**：作者先說研究問題與限制 → 搜尋不同觀點 → 保留選擇與否決原因 → 按問題比較 → 確認暫時主張。
3. **既有稿件起步**：匯入 Word → 人工核對章節與素材 → 建立版本 → 補缺少的來源及研究界線；不先讓 AI 改寫全文。
4. **師生修訂**：教授對某版本、某主張留意見 → 作者回覆與修訂 → 教授看差異與來源 → 確認處理或繼續討論。
5. **中斷恢復**：離頁、斷線或重啟 → 回到原專案看到保存與任務狀態 → 續做或只重跑失敗階段。

## 6. Chain of Context：人類決策與證據的交棒

### 6.1 兩個既有層次

`ContextChainService` 保存分層脈絡、檢索提示、知識關係與變更狀態。Manuscript 的 `coc_bundle`／`coc_producers` 重新收集本章正文、先前對話、可讀章節、人工納入與理由、PAQ 資料及版本留言；`ManuscriptRuling` 另帶入研究筆記與段落證據。

現況是「寫作時收集部分來源」，不是所有模組的每一輪對話都完整連接。新增設計須重用這些入口，不另建一條繞過納入規則或章節權限的資料路徑。

### 6.2 最小決策資料契約

下列為**目標欄位**，可擴充既有記錄與指紋，不代表必須建立新資料庫或把全部聊天複製到各模組。

| 資料 | 目標內容 |
|---|---|
| 身分與範圍 | decision_id、project_id、module、section／claim、伺服器確認的操作者 |
| 來源角色 | 人類原文、AI 提案、人類修訂；AI 提案被採用時仍保留來源與確認者 |
| 主張與理由 | 要表達什麼、為什麼、採用／否決哪些選項、需要保留的限制 |
| 證據與條件 | paper／segment／page／figure 等定位、數值與單位、樣本／幾何／資料集等適用條件 |
| 狀態 | proposed、confirmed、rejected、superseded；事實支持度另標 supported、insufficient、contradicted |
| 版本 | 作者修訂版、來源指紋、時間、取代哪筆決策、影響哪些下游稿件 |
| 可見範圍 | 個人草稿／專案共享／章節限定；沿用現有後端 ACL |

「作者確認」表示作者認可表述或研究方向，不等於假設已獲證實。遇到證據衝突須提示，不可因為是人說的就把假設寫成事實。被排除文獻的拒絕決策可保留為流程紀錄，不得藉此把其內容重新當成正式支持證據。

### 6.3 生成時的順序與結果檢查

先辨認作者本輪合法要求、已確認主張、禁止擴大的範圍與未處理審閱意見，再選擇支持／反駁證據。原始論文與 AI 歷史屬來源資料，不能夾帶越權指令；作者合法的本輪要求不應與來源內的注入文字一律視為不可遵循。

空間不足時，系統先保住核心決策及必要限制，選取相應證據；不得只保留前文摘要而刪掉條件。若核心決策與必要證據無法一同容納，應縮小單次生成範圍或請作者選擇，不假裝已完整處理。

生成後以差異檢視列出：保留／改動的作者主張、AI 新增推論、未支持或矛盾處、未處理的審閱意見、引用缺口。AI 自評只能作提醒，不能作最後通過依據。作者確認後才晉升為供下游使用的確認稿。

### 6.4 作者聲音

作者聲音包含論證順序、關注的問題、取捨與慣用表達。可由作者指定少量已確認段落及本專案用語作參考；不自動抓取他人或其他專案內容。提供保守潤飾、結構重整、重寫等明確操作，改動幅度可見、原文可還原。

不以 AI 偵測分數驗收。評估作者關鍵決策保留、未授權新增主張、改稿量，以及作者／教授對內容忠實度的核對。

## 7. 需求目錄

優先度 P0：先封住已重現的多人影響或資料風險。P1：主要研究工作與交付所必需。P2：改善理解、效率與品質量測。所有列均為本版**目標要求**；現況見問題／證據與驗收矩陣。

### 7.1 使用者流程與介面

#### UX-01｜依研究工作導航（P1）

主入口使用研究定位、文獻庫、閱讀與比較、寫作、輸出、審閱與回覆。專案、目前章節與保存狀態持續可見；內部編號、Task ID 與檔案路徑移到進階診斷。建立專案先收必要資訊，人員完整履歷與投稿作者資訊可稍後補。

#### UX-02｜單一文獻項目與入口（P1）

搜尋、DOI／書目匯入、PDF 上傳均進同一清單；文獻身分、PDF／版本、處理成果與篩選決策可相連。重複項目提示合併但不靜默丟棄，直接上傳預設 candidate；必須保留既有 paper_id／entry_id 可追溯關係。

#### UX-03｜讓人能留下選材理由（P1）

在文獻條目、原文選段與比較格中可新增／修訂採用理由、否決原因與研究筆記；可看見作者及修改時間。理由必須可由一般介面完成，不要求貼 JSON。文獻納入後仍要對每個寫作主張核對支持範圍。

#### UX-04｜處理選項對應研究需要（P1）

將單篇／批次處理呈現為明確用途：可檢索與核對、全文翻譯、深度比較等；顯示即將使用的外部服務、費用是否可估與預期限制。沿用已授權預算自動前進，超出上限才停下；不把每個內部階段的排程責任交給研究者。

#### UX-05｜閱讀優先與可及操作（P2）

原文、譯文、重排與 AI 解讀可辨別並互相定位；作者能選取原文存筆記，不必先產生矩陣。提供與 3D 等價的表格操作、鍵盤焦點、文字狀態及可放大閱讀；繁體中文與英文送出鍵須正確處理輸入法組字。核心流程在 1280×800 視窗及 200% 字級可到達主要控制，實際驗收後才標示通過。

#### UX-06｜真實狀態與校準信任（P1）

把運算處理、人工審核、保存、主觀進度分開呈現。RPI 顯示為可修訂的研究潛力建議與理由，不當成成功率或證據強度。登入時間不當研究品質指標；全站 ready／complete 不只依檔案存在。首頁優先呈現待我處理與阻塞原因。

### 7.2 人類決策鏈與作者性

#### COC-01｜來源角色與決策狀態（P1）

每項可往下游交棒的主張／取捨帶有第 6.2 節的最小身分、理由、來源與版本。AI 產出預設 proposed；只有明確作者操作可標 confirmed。確認者由伺服器決定，不接受請求偽填。人類假設與證據支持度分開保存。

#### COC-02｜全模組交棒覆蓋（P1）

PAQ 的決策、文獻理由、Study 經確認的比較與多輪對話結論、研究筆記、Manuscript 修訂及教授意見可在下一步被引用。只交接與當前工作相關且有權限的內容；未確認 AI 對話不因被複製就升級成作者觀點。作者能看到本次使用及缺少的脈絡。

#### COC-03｜逐段主張與證據界線（P1）

生成段落前可指定本段目的、主張、適用條件、證據與不能聲稱的事；支援從已確認筆記一鍵建立。保留「作者決定 → 段落 → 引用」關係，避免每次都從題目重新寫一段泛泛介紹。

#### COC-04｜預算下保留核心決策（P1）

核心作者主張、限制與當前工作需要的證據有優先級；上下文截取依問題與來源定位，不只取最前面。裁切／跳過可見且寫入來源清單；清單須與最後送出的內容一致。無足夠預算時縮小工作範圍，不輸出缺關鍵條件的完整結論。

#### COC-05｜版本與影響範圍（P1）

修正問題、篩選、證據或主張後，標示受影響的筆記／矩陣／段落／引用／輸出需重核。舊版本及未解決意見保留；意見跨版本由作者確認對應或標為已不適用，不能因換版就無聲消失。確認內容被 AI 改寫後重新回到待核狀態。

#### COC-06｜保留作者聲音與合法要求（P1）

支援原文保留、保守潤飾與重整的明確選擇；作者指定用語、段落樣本與論證順序在本專案範圍生效。最終提示詞清楚區分使用者合法要求與來源資料內的指令，不以統一模板抹去作者風格。不得新增沒有研究依據的個人經驗。

#### COC-07｜主張、來源與引用一致（P1）

正式寫作與引用建議遵守同一人工納入規則；探索候選需明示，不直接採用為正式證據。每個引用能回到原始片段、位置與指紋，顯示支持範圍與不支持的延伸。資料變動後提示重查；真正操作者不可由用戶端冒填。

#### COC-08｜生成後忠實度核對（P1）

生成結果顯示作者決策的保留／遺漏、AI 新增主張、條件改變、證據衝突與未處理意見。作者可接受局部修改並還原。以人工核對、關鍵決策保留及未授權新增主張衡量，不以偵測器分數或模型自評宣告人類作者性。

### 7.3 研究方法與內容功能

#### RES-01｜可修訂的研究簡報（P1）

專案至少能表達研究類型／領域、研究問題、假設或待探索問題、資料／樣本、比較基準、主要結果指標及限制。依探索、實驗／模擬、方法比較或文獻綜述提供輕量引導；允許不適用與待定。Cube 為可選檢視，不能成為唯一思考方式。

#### RES-02｜依問題比較並選定基準（P1）

比較前讓作者指定基準、問題與維度；文獻清單順序不得默默決定學術基準。從相關全文片段取證據並回到原位置；不固定只取每篇前 2,500 字元，也不強迫所有問題輸出同一五維、同一短字數。自訂欄位與人工修訂可保存及交棒。

#### RES-03｜可比較條件與矛盾（P1）

比較格保留數值、單位、指標定義、樣本／資料集／器件幾何等必要條件與模擬／量測身分。條件不相容、資料缺漏或來源矛盾時明示，不自動選出優勝方法或合併數字。跨研究數值綜合需要另外明確的方法與確認。

#### RES-04｜可重做的領域搜尋（P2）

保存問題、查詢、來源、日期、篩選條件及候選／排除理由；真實來源回查、查無結果與來源服務失敗分開。Scout 角度依專案問題／領域設定，不固定醫學或神經科學。文獻存在與 DOI 正確不等於其支持了某個主張。

#### RES-05｜多輪研讀與研究結果形成主張（P1）

Tutor 帶入近期對話、目前聚焦與已確認筆記，回答能定位原文後段結果；無答案就明示。比較與研究紀錄可轉成待核主張；匯入自己的實驗／模擬結果時保留條件、版本與資料角色。AI 示意圖、假資料與提議的實驗不得當成已完成量測或真實結果。

### 7.4 協作與審查

#### COL-01｜角色與可見範圍（P0）

學術角色、專案操作權限及系統管理權限明確分開。模組頁面、API、Socket、匯出與模型請求採一致後端判斷；共同作者不藉上下文看到未授權章節。個人草稿轉共享有明確操作；新舊帳號切換不沿用其他人的脈絡。

#### COL-02｜師生審查閉環（P1）

教授可選稿件版本、看前後差異、定位主張／證據並留意見；作者可看到同一意見、回覆、連結修訂位置，教授可確認已處理或要求再修。資源附件雙方按權限可取用。優先串接現有 ChapterComment 與 Mentor 回饋，不另造互不相通的留言系統。

#### COL-03｜我的工作與審查範圍（P2）

各角色看見被指派的章節／決策／回覆及阻塞原因；待辦連回相同專案、版本與意見。避免兩處各自保存互相矛盾的狀態。多人審查可分辨誰的意見、誰可確認，不以活動統計替代任務結果。

### 7.5 投稿輸出

#### SUB-01｜第一條完整輸出路徑（P1）

重用現有 DOCX 與素材解析能力，先把 Submit 接到選定的全文版本。引用採用、正文引用與文末書目要有可檢查的一致關係；圖表公式、caption、編號與作者資訊可核對。缺圖或格式不支援時阻擋或明示，不默默漏掉。

#### SUB-02｜固定版本與輸出清單（P1）

輸出保存稿件／章節版本、模板與版本、引用來源、素材及輸出雜湊；提供預覽與可攜下載。第一個模板通過後才擴充其他格式，未完成的選項明示。作者貢獻、AI 使用聲明等由人確認，不憑推測填寫；輸出不自動投稿。

### 7.6 可靠性與原有能力保護

#### REL-01｜保留原件與安全接續（P0）

原 PDF、作者手稿、歷史版本與既有 ID 保留。兩份文獻清單合併或補登記時只建立 candidate，不偽造人工納入；保留舊 reader／路徑相容直到驗證遷移。實作與測試用隔離資料；不把原有失敗改寫成新增回歸或通過。

#### REL-02｜可恢復長任務（P1）

用既有資料能力保存 job_id、輸入指紋、階段、狀態、結果位置與重試資訊。重啟後可辨別已完成、待恢復與可重試；不重複消耗已完成步驟。取消向下傳遞且回報 provider 是否真的停止；不能保證取消不計費時明示並照實記帳。

#### REL-03｜保存與衝突（P0）

共用筆記、對話追加、章節與來源決策採適合範圍的版本比對／原子更新；個人草稿沿用現有隔離。舊分頁不能無聲覆蓋較新內容；失敗時保留可恢復文字，確認保存後才顯示已儲存。

#### REL-04｜成功、部分成功與降級（P0）

分開回報運算結果、品質模式及保存結果。全部比較失敗不能回研究分析成功；規則提示明示用途並保留原失敗原因。Provider、索引、磁碟故障不包裝成正常答案或空結果；部分成果可檢查、下載或只重試缺項。

#### REL-05｜服務可工作與資料恢復（P1）

區分程序在線與 DB／必要服務／佇列可工作；健康訊息不含秘密。以隔離工作負載測試容量與資源界線，在單程序記憶體狀態與本地模型限制解決前不直接增加 worker。整套資料在一致版本下備份還原，驗證稿件、來源、決策與附件可互相定位。

#### REL-06｜研究品質基準（P1）

建立代表性雙欄、掃描、表格、公式及 caption 樣本，檢查文字、數字／單位、閱讀順序與定位。檢索問題集涵蓋中英同義詞、後段答案、跨篇條件、被排除資料、無答案與矛盾；分開量召回、定位正確與主張支持。取得基線前不宣稱科學品質已通過。

### 7.7 全站模型與費用

#### GOV-01｜全站模型管理守門（P0）

`/api/llm` 的連線、綁定與 runtime 設定寫入需要明確系統管理權限；設定頁與全部對應 API 一致。一般使用者／限定編輯不可新增或刪除全站連線。保留合法研究任務使用既有模型的能力，變更者由伺服器記錄，輸出仍遮罩秘密。

#### GOV-02｜能力、用量與預算（P1）

任務按實際需要檢查文字／圖像／搜尋能力，模型綁定綠燈只代表特定連線測試。用量記錄保留專案／任務／模型及是否快取、重試、取消；未知價格標未知。先估計可估範圍、依已授權預算執行，超限才要求決定，避免重試暴增或長任務無限排隊。

## 8. 技術架構與依賴

延續本地優先 Flask 3.x、Flask-SQLAlchemy、Flask-SocketIO、SQLite／檔案成果、Gunicorn、Docker 與可設定 Redis。即時模式依環境可使用 threading／eventlet，正式 worker 設定需以部署檔與驗收結果為準。Redis 的訊息傳遞不等於程序內任務已持久化。

技術資料流：Browser → 模組 API／Socket → 領域服務 → CoC／Evidence／LAVA 或本地處理 → SQLite／檔案成果。人類決策與來源版本在模組邊界可追溯；ACL 在後端執行。

主要既有依賴保留：Flask 系列、SQLAlchemy、filelock、cryptography、requests、Google／OpenAI adapters、Pillow、OpenCV、pdf2image、Poppler、Tesseract、EasyOCR、layoutparser、NLLB／transformers／sentencepiece。未因本文件增加依賴；實作先重用現有服務及標準庫。

## 10. 狀態、版本與權限契約

| 對象 | 必須分開的狀態 |
|---|---|
| 文獻 | 身分／PDF 是否存在／處理進度／candidate-included-excluded／對某主張的支持度 |
| 任務 | queued-running-completed-partial-failed-cancelled／保存結果／降級模式 |
| 主張 | proposed-confirmed-rejected-superseded／supported-insufficient-contradicted |
| 稿件 | 個人未存草稿／章節版本／全文版本／待審／已確認／需重核 |
| 審查 | 開放／作者已回覆／教授確認完成／明示不再適用 |
| 輸出 | 指定來源版本／模板版本／產物／驗證結果；不是外部投稿成功 |

這些為語意契約，不要求一次更換所有舊狀態字串。實作以相容方式映射、逐一替換真實使用入口。狀態查詢保持唯讀，不觸發付費任務、OCR、重寫或修復。

## 11. 驗收情境與品質判準

完整案例、需求對照與證據欄位見 `docs/ACCEPTANCE_MATRIX.md`。下列均為待實作後執行的目標驗收，不能由既有 unit test 通過自動認定完成。

| 案例 | 核心情境 | 必須看到的結果 |
|---|---|---|

## 13. 實作與交付規則

1. 先對照需求、實際入口與呼叫端；重用既有 helper、讀取器、版本及匯出。
2. 保留原始資料與不相關變更。遷移、刪除、部署、發送及付費行為按使用者授權範圍另行處理。
3. 測試使用合成／獲授權樣本與隔離 DB，不載入正式金鑰、論文、日誌或模型到版本庫。
4. 修正不可把科學條件、省略來源、個人草稿隔離或章節 ACL 刪掉來縮短差異。
5. 每次交付寫明需求 ID、變更、驗證、剩餘限制；更新驗收矩陣的證據，不先把全部目標標成通過。
6. 文件更新、程式實作、部署、研究品質與外部投稿為不同完成狀態。
