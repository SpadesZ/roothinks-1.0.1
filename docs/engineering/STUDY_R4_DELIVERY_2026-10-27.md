## 1. A 安全熱修候選（摘要）

- **H1**：`runtime_log_tail` 沒有 pid，專案 ACL 不會執行，任何登入者都能讀全站日誌。修補後只有系統管理員可讀：
  - session 模式要 `system_role=admin`；
  - Bearer 模式要 token 在 `TOKEN_ACL_MAP` 中明確寫 `system_role=admin`，專案 wildcard 不算。
- **H2**：`flowb_probe` 與 `recover_flowb` 會把其他專案的日誌行給本專案成員。修補後只回本專案 pid 的行，不回伺服器路徑。
  pid 比對用嚴格字界，`_` 和 `-` 也算字界。
- 測試：13 個新測試。還原修補後有 9 個失敗（紅測試成立）。
- 完整回歸：Python 3.10（main 正式映像的版本）與 3.12 都跑過。修補前後的失敗清單**逐行相同**，只有 1 個既有失敗（user journey 測試替身參數不符）。
- 部署設定（只讀檢查）：
  - GCP compose 用 session 模式；prod compose 預設也是 session 模式，另開 Bearer。
  - 部署前要確認至少有一個 admin 帳號。
  - 回滾：revert 這一個 commit 即可。沒有資料庫遷移，也沒有新設定。
- **歷史暴露**：不能宣稱沒有發生過。
  - 兩個問題從 2026-06-30 起就存在。
  - 前端沒有呼叫這兩個端點，所以只有手動送出的請求會觸發。
  - gunicorn 存取日誌（stdout／Cloud Logging）可以查到呼叫紀錄，但沒有使用者身分。
  - Owner 需要在正式日誌副本上跑 `scripts/security/log_exposure_audit.py`。

## 2. B1 寫入／匯出／下載／間接存取權限矩陣

`test/integration_e2e/acl_write_matrix.py`：

- **範圍**：列舉全部 84 條 POST／PUT／PATCH／DELETE 路由，共 434 次請求。
- **角色**：
  - 外人、教授（審閱身分）、舊導師、團隊 viewer；
  - editor（只測 owner 專屬動作）；
  - 間接存取的外人：用自己的 pid，但其他 id 指向 ACLP1 的物件。
- **請求內容**：body 帶齊常見欄位。遇到 409 就換 base_rev 重送，避免因為版本號錯而誤判為安全。
- **判定方式**：比對 ACLP1 所有檔案與資料庫列的指紋，指紋改變就是發現。每次發現後重建整個世界。

## 3. B2 日誌結構化出處

- 每一行 `runtime.log` 帶 `[pid=<專案>]`（`app/log_provenance.py`）。
- 這個值只來自伺服器設定，不用請求參數：
  - 授權成功後的請求；
  - 背景 worker 的 usage contextvar；
  - Flow B 子程序的 `ROOTHINKS_LOG_PID`。
- 被拒絕的請求維持 `[pid=-]`，所以外人不能把文字寫進別人的日誌視圖。
- Flow B 快照只看出處欄位。別的專案的行就算文字提到本 pid 也不給。升級前的舊行沒有標記，一律不給，並且計數。
- 本專案不含 pid 文字的行現在也看得到了；子字串比對做不到這一點。

## 4. B3 Manuscript 段落級出處

- **連結方式**：已保存的一段可以連到 Study 證據筆記，或標成「自由寫作，未連結已核對證據」。
- **連結時保存筆記的快照**：
  - 引文與錨點；
  - AI 解讀、研究者假說；
  - 研究者的支持判斷、AI 不確定性；
  - 修訂次數。
- **讀取時計算狀態**：`paragraph_changed`、`note_revised`、`note_missing`、`source_changed`、`source_unavailable`。
  這些都只是提示，**不擋寫作、保存、匯出**。瀏覽器測試證明：有出處的段落仍可改寫並保存成新版本。
- **存放與權限**：
  - 只追加，撤回也是追加一筆紀錄；用 `_rev` 加歷史快照。
  - 章節層 ACL：讀和寫按章節判斷；整份匯出要能讀全篇。
  - 筆記選單只給 owner／editor。
  - 教授只看得到已請求審閱的筆記內容。
- **介面**：
  - Manuscript 有「段落出處」面板與 Markdown 出處紀錄匯出；
  - Study 筆記卡和教授工作台都顯示「用在稿件哪一段」。
- 與既有嚴格段落契約（`paragraph_context.py`：文獻已納入、證據已索引、PDF 指紋）分工。兩者尚未合併成一個流程。

## 5. B4 翻譯保護層邊界案例

| 問題 | R3 行為 | R4 |
|---|---|---|
| 同一句兩個相同公式，丟掉一個 | 判定為沒有遺失（負向控制證明 R3 看不到） | 依佔位符編號追蹤，抓得到 |
| 編號被改成不存在的號碼、或被刪掉 | 殘渣留在譯文，片段補到句尾 | 孤兒數量等於遺失數量時，在原位置還原；否則刪掉殘渣，補到句尾並標示 |
| 同一佔位符被輸出兩次 | 公式插入兩次 | 只還原一次，記錄重複 |
| 還原進去的原文含像佔位符的文字 | 會被再掃一次 | 單次掃描，不再掃 |
| 底線整個被刪掉（`RTK KEEP 0`） | 認不出 | 認得 |

量測（**模擬**）：新增 6 句重複片段語料與 3 種損壞型態。結果：0 句無聲遺失、0 句殘渣、忠實引擎 0 誤報。

## 6. B5 閱讀、筆記與師生流程

- **雙語閱讀**：
  - 每段譯文在閱讀時檢查。原文中的「量測型」數字（有小數點，或兩位數以上）在譯文中找不到時，顯示「請以原文為準」。
  - 有遺失片段被補回時，也會提示。
  - 單位數字不比對：中文常把 3 runs 寫成「三次」，比對會誤報。
  - 提示放在可選取的譯文外面，不會混進證據引文。
- **fixture**：加了一段故意寫錯數字的機器翻譯。瀏覽器測試要求恰好 1 個提示，也就是其他段落 0 誤報。
- **教授工作台**：請求審閱的筆記會顯示它用在稿件哪一段。
